# Phase 1の具体的な実装計画

状態：未着手・ユーザー承認待ち。対象実データの提供元が未確保のため、以下は条件付き計画です。

## 1. 方針と開始条件

推奨は「正式API／許諾を確保して本来のMVPを作る」案です。NAVITIMEの時刻表APIを候補にしますが、長沼営業所の対応、必要な時刻項目、リアルタイム情報、利用許諾を実応答で確認するまで採用確定しません。対象GTFS／GTFS-RTが別途提供される場合も同じ手順で検証します。

開始条件は、ユーザーによる方針承認と、提供元からの対象データ・必要な利用権限・接続条件の確保です。費用が必要な契約の申込や外部への問い合わせ送信は別途明示的な指示を受けて進めます。

実データ取得が成功するまでは、UIのサンプルを作っても「対象データで動くMVP」と判断せず、運行情報サイトとして公開しません。今回は調査資料だけを追加しています。

| 工程 | 実装・確認内容 | 完了条件 |
| --- | --- | --- |

| 1-B 正規化と抽出 | 運行日・stop_sequence・乗降可否による直通便抽出、時刻と予測種別の統一 | 他方向・稲33・目的地非停車便が混入しない |
| 1-C 時刻計算 | 乗車まで・到着まで・乗車時間・遅延・到着順比較 | 下記の情報種別・欠測ルールと意味のあるテストに合格 |
| 1-D 画面 | 方向切替・保存、直近便、後続便、順序切替、地図／区間／不明表示、手動更新 | スマートフォン縦画面とPCで操作・読み取りができる |
| 1-E 更新・障害 | 共有キャッシュ、許諾内更新、非表示抑制、リトライ抑制、期限切れ・運休等 | 取得失敗・古い情報でも画面が操作でき、情報種別が正しい |

## 3. 構成

React・TypeScript・Next.jsを基本候補とし、サーバー側に取得元adapterと正規化処理を置きます。ブラウザは自アプリの`GET /api/board?direction=outbound|inbound`を読み、提供元の秘密情報を受け取りません。ホスティングは正式APIの接続元制限・契約条件に適合するものを選びます。

| 層 | 担当 |
| --- | --- |
| provider adapter | 契約APIまたはGTFS／GTFS-RTの取得・認証・スキーマ検証。利用条件も設定として保持 |
| transit domain | 運行日・方向・直通性の判定、同一便照合、時刻の優先順位・遅延伝播、並び順 |
| server API／cache | 両方向で共有した上流取得、レート制御、期限・観測時刻の管理、公開用JSON |
| client UI | 方向保存、残り時間表示、便の選択、手動更新、非表示抑制、アクセシビリティ |
| map | Leaflet＋利用条件を確認したタイル。GPS実測値と停留所だけを座標表示。区間情報は別表示 |

提供元を追加・交換するときはadapterとID対応表を変更し、画面・計算部分への影響を抑えます。認証情報・署名・生レスポンスをブラウザのソースや公開Git履歴・ログに残しません。

## 4. 保持する正規化データ

| 対象 | 必須の意味 |
| --- | --- |
| 便 | provider・feedVersion・tripId／operationId・serviceDate・必要に応じstartTime・系統・行先・方向・運行状態 |
| 停留所 | 取得元別ID・標柱・stop_sequence・乗降可否。往復は標柱単位で対応確認 |
| 個々の時刻 | scheduled／effective、arrival／departureの区別、`realtime`／`delay_estimate`／`timetable`、sourceObservedAt、根拠となる遅延 |
| 位置 | `gps`（緯度経度・測位時刻・便照合）／`stop_segment`（区間・観測時刻・正確な座標なし）／`unavailable` |
| 更新状態 | fetchedAt・最終成功取得時刻・提供元観測時刻・有効期限・stale・通信エラー・時刻表期限切れ |

GTFS利用時は便識別にtrip_idだけでなくserviceDate・必要なstart_time・フィード版を用います。NAVITIMEでは運行IDが更新される仕様のため、永続固定IDとは扱わず、契約仕様に従い再取得します。[停車駅一覧仕様](https://api-sdk.navitime.co.jp/api/specs/api_guide/transport_stops.html)

## 5. 抽出・計算・表示ルール

1. `agency`・正式なroute対応・運行日・乗降停留所の順序と乗降可否を確認し、直通便だけを採用します。direction_idや系統番号の一致だけでは決めません。目的地を通過する便は除外します。
2. 乗車・目的地それぞれの時刻は「有効な対象停留所のRT」→「仕様上許された遅延反映推定」→「時刻表」の順に選択し、個々の値に種別を表示します。片方だけRTというケースも明示します。
3. RTが欠ける便の遅延は「不明」とし、ゼロにしません。GTFS-RTの`NO_DATA`・`SKIPPED`・`CANCELED`等を尊重し、遅延を下流へ無条件で加算しません。[GTFS-RT Trip Updates](https://gtfs.org/documentation/realtime/feed-entities/trip-updates/)
4. 乗車時間は「同一便の目的地到着 − 乗車停留所出発」で計算します。出発予測がない場合、到着予測を同値で代用してよいという提供元の根拠がなければ推定乗車時間は出しません。有効な予定出発・予定到着が両方あるときは「時刻表上の乗車時間」を別に表示します。
5. 乗車までの残り時間は有効な出発時刻を基準に分単位で表示します。到着時刻しか分からない場合は「停留所到着まで」に文言を変えます。目的地までの残り時間は有効な目的地到着−現在時刻です。負の所要時間等の矛盾データは除外して警告します。
6. 稲31・稲32を統合し、今後の乗車可能な便を時系列に3便以上（存在する範囲）表示します。便数不足を補う架空便は作りません。目的地到着順でも比較でき、後続便の先着予測を控えめな注記で知らせます。
7. GPSは同一便への照合に成功した実座標と測位時刻のみ表示します。車両IDだけによる折返し便の誤照合を防ぎます。接近区間のみなら「GPS座標なし」を明示した区間表示とし、道路上に推測マーカーを置きません。
8. `Asia/Tokyo`で営業日・実日付を扱います。GTFSの24時以降を翌暦日の絶対時刻に変換し、calendarとcalendar_datesを適用します。前日営業日の深夜便も検索し、曜日だけで祝日ダイヤを決めません。NAVITIMEの日付は当該node出発日という仕様に合わせます。

## 6. 更新と画面

初期候補は30秒ですが、上流の更新周期・許可頻度を最優先します。サーバー側で取得を集約し、閲覧者数や手動更新の回数で上流へのリクエストが増えないようにします。失敗時はバックオフし、429のRetry-After等に従います。

画面非表示中は定期取得を止めるか許可範囲で減らし、復帰時に取得します。方向切替時は前のリクエストを中断・無効化し、遅れて返った他方向の便を混在させません。localStorageが利用できない場合も方向切替を利用できます。

鮮度は提供元の観測時刻を基準とし、受信時刻だけで「最新」にしません。閾値は提供条件を確認して設定します。観測時刻不明なら鮮度不明と表示します。古いRTは警告付きにするか予定値へ切り替え、古い座標を現在地として扱いません。通信障害、RTなし、位置不明、運行なし、運休、期限切れは別状態です。

画面は方向切替、直近便の大きなカウントダウンと目的地到着、乗車時間、後続一覧、地図／区間表示、更新情報の順にします。日付をまたぐ時刻には翌日等を表示します。ボタン等の`touch-action: manipulation`で意図しないダブルタップを抑え、`user-scalable=no`は使わず、文字拡大と地図のピンチ操作を維持します。

## 7. 受入テストと公開条件

| 要件に対応する試験 | 検証方法 |
| --- | --- |
| 両方向の稲31・稲32と目的地停車 | 対象の許諾済み実応答を公式情報と照合し、停車順・乗降可否・運行日を検査 |
| 方向混入・目的地非停車便の除外 | 逆順、異なる標柱、稲33、目的地なし・通過のケースを抽出処理で確認 |
| 同一便の両停留所 | trip／operationId・運行日・停車順で結合し、同時刻の別便を混ぜない試験 |
| 残り時間・乗車時間・順序比較 | 固定時計で日またぎ、片方欠測、負の値、後続便先着を確認 |
| RT・推定・予定・遅延不明 | 片側RT、NO_DATA、運休、遅延伝播停止、出発予測欠測の試験 |
| 古い情報・通信失敗 | 古い観測時刻、上流タイムアウト、429、5xx、不正JSON、期限切れ時刻表を再現し操作継続を確認 |
| GPSの正確性 | 実座標・測位日時・便照合を確認。区間のみ／位置なしでは正確なGPSマーカーを表示しない |
| 自動・手動更新 | 非表示中抑制、復帰、方向切替中の競合、複数閲覧者の共有キャッシュを確認 |
| Android・Windows | モバイル幅とデスクトップ幅でブラウザ操作を確認し、Android ChromeとWindows Chrome／Edgeの実機確認の実施有無を別途記録 |

計算ロジックのテストや疑似障害試験は使いますが、対象実データでの結合検証の代替にはしません。Linux上のブラウザや端末エミュレーションをAndroid・Windows実機の合格と表記しません。

公開前に、対象実データの取得成功、必要機能・許諾範囲、テスト、ビルド、出典表示、秘密情報の非露出、ホスティングからのAPI接続を確認します。合格後はユーザーの「テストで問題なければ公開」の指示に従って配信し、URL・検証範囲・残る制約を報告します。

PWA・お気に入り・予測と実測の比較はPhase 2に残します。

## 8. 縮小案を承認した場合

公式リンク中心の簡易版では、方向保存と公式の時刻表・接近情報への導線を作り、独自の時刻・位置・遅延は表示しません。外部ページは直接開き、自動取得・転載・iframe埋め込みをしません。この案は本来のMVPとは別の承認対象です。

時刻表のみの許諾を得た場合は、予定時刻と「時刻表上の乗車時間」を表示し、遅延・現在位置は不明とします。RT到着予測・先着予測・地図上の車両位置は達成済みにしません。
